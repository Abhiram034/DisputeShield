# DisputeShield build notes

Completed: Phases 1–4 (Compose/PostgreSQL, checksummed migrations, reproducible synthetic data, deterministic risk scoring), Phase 5 (persistent case detection/list/detail), Phase 6 (merchant-scoped read-only investigation tools), Phase 7 (bounded optional structured investigation agent), Phase 8 (normalized investigation evidence and evidence presentation), and Phase 9 (authoritative deterministic policy engine). Migration 005 adds tenant-scoped evidence fields. `GET /api/cases/{id}/investigation-tools` distinguishes known results, successful empty results, and failed sources; it is read-only. `POST /api/cases/{id}/investigate` stores a validated report plus evidence references, or marks AI unavailable and escalates for human review. `GET /api/cases/{id}/evidence` returns the latest investigation's source fields for that merchant.

The risk API is `POST /v1/risk/assess`. Scoring and thresholds are in [RISK_ENGINE](RISK_ENGINE.md); case lifecycle/tool contracts are in [CASE_MANAGEMENT](CASE_MANAGEMENT.md); deterministic gates are in [POLICY_ENGINE](POLICY_ENGINE.md); action workflow details are in [ACTION_ENGINE](ACTION_ENGINE.md).

Current boundaries: action execution only records a simulated result and never contacts external systems. The LLM provider is optional and disabled by default. `merchant_id` and actor IDs are local demo scopes, not authentication; keep this local-only until an auth gateway is added.

`POST /api/cases/{id}/policy-check` and `POST /v1/policy/check` use the latest persisted policy and case facts, return a reason code and evidence references, and append an audit row. Migration 006 adds the merchant's maximum evidence age. Policy outcomes distinguish eligible, human review required, and blocked.

Phase 10 is complete. `POST /api/cases/{id}/actions` creates an idempotent policy-gated recommendation. `POST /api/cases/{id}/interventions/{id}/approval` records one human approval or rejection. `POST /api/cases/{id}/interventions/{id}/execute` rechecks policy and persists a simulated result with `external_side_effect=false`. Migrations 007–008 add merchant-scoped idempotency, request fingerprints, approval records, simulation results, and remove the earlier global key constraint. The old unscoped execute route returns 410.

Phase 11 is implemented. Simulated execution creates one merchant-configured 1–365 day observation window per intervention. `GET /api/cases/{id}/outcomes` lists persisted outcomes; `POST /api/cases/{id}/outcomes/refresh` reconciles only persisted disputes and post-payment events, stores evidence IDs, and audits each refresh. A missing dispute remains unknown until the observation window ends; after that it is recorded as “no dispute observed,” never as a prevented dispute. Migration 009 adds window bounds, lifecycle status, refresh evidence, and the merchant observation duration.

Phase 12 is implemented. Migration 010 adds merchant incident thresholds and a tenant-scoped incident ledger. `POST /api/incidents/detect` calculates persisted dispute rates for a current window and the preceding baseline, and opens a `DISPUTE_RATE_SPIKE` only when merchant thresholds are met. Overlapping open incidents return the existing incident as a conflict and record an audit event. `GET /api/incidents` lists a merchant's incidents; `POST /api/incidents/{id}/status` supports audited acknowledge and resolve transitions.

Phase 13 is implemented. `apps/web` is now a Next.js/TypeScript dashboard, served on port 3001. It selects a merchant, loads cases and incidents from the API, supports incident acknowledge/resolve, and refreshes selected case observation windows. Merchant setup creates a default policy through the API. An empty merchant workspace can be deleted by typing its exact name; deletion is refused if customer, transaction, order, payment event, dispute, case, or incident records exist. No fabricated case rows, metrics, or prevention claims are displayed. Next.js proxies `/backend/*` to the API container, and the UI describes the local-demo/auth boundary.

The generated synthetic CSV fixture is loaded by `scripts/load_synthetic_data.py`. The current full import has 10 synthetic merchants, 5,000 customers, 50,000 transactions, 50,000 orders, 100,000 events, 601 disputes, and deterministic risk assessments/cases. Fixture IDs map to stable UUIDs; source event tenant IDs are reconciled to their transaction. The import is additive and idempotent, and leaves non-fixture merchants untouched.

Next: Phase 14 simulation engine, followed by evaluation and deterministic experiment assignment.
